# Component-descriptor formats — cross-format deep-dive

> A field-by-field study of **ten** component/element descriptor formats, run as primary-source research to inform a **greenfield** component/element descriptor format for ng-objects (and a possible evolution of the WebObjects element format). Each format was observed **on its own terms as industry practice** — explicitly *not* mapped onto, or constrained by, current WO/ng conventions. The goal is best-in-class ideas, including ones that would replace what we do today.

See [`../proposal-tag-library-format.md`](../proposal-tag-library-format.md) for the higher-level summary and the original survey this deep-dive expands.

## Cross-cutting findings

### What every format declares

Across all ten formats, an irreducible core recurs: every format names an **element** (by tag, selector, export name, or CLR type) and enumerates its **inbound configuration surface** (attributes/props/parameters) with at minimum a *name*, and usually a *type*, a *default*, a *required* flag, and a human *description*. This is the shared floor. Above that floor, the formats diverge sharply in how much of the element's *other* surfaces they bother to model — and the most striking cross-cutting finding is that the better-regarded formats refuse to treat an element as "a tag plus a bag of attributes." Custom Elements Manifest, web-types, Stencil, Vue, JSF, and Blazor all converge independently on the same insight: an element exposes **several distinct, separately-typed channels** — inbound props, outbound events, content-projection points (slots/facets), imperative methods, and styling hooks (CSS parts/custom-properties/states). A flat binding list (the WO/ng `.api` model, and the deliberately-minimal VS Code custom-data model) is the outlier, not the norm. The field has collectively learned that conflating these channels is a modeling error.

### What splits runtime / tooling / both

The formats cleave cleanly into three roles, and the role predicts almost everything about the format's shape. The **tooling-only** formats (CEM, web-types, Stencil JsonDocs, Vue meta, VS Code custom-data) are overwhelmingly *generated from source by an analyzer*, optimize for emission rather than hand-authoring, and carry no runtime authority — which is precisely why several of them (Stencil explicitly, CEM by omission) can document slots or parts that the implementation never renders. The **code-is-the-descriptor** formats (Angular, Blazor) eliminate drift entirely by making the metadata *be* the implementation, but pay for it with total host-language coupling and no portable artifact. The **runtime+tooling** formats (JSP TLD, JSF, and Svelte by its `runtime+tooling` role) are the only ones that serve both masters from one source — and they are the only relevant precedent for what Parsley actually wants, since the current ng/Parsley descriptor is read by *both* runtime and tooling from one source. The lesson is not subtle: a single artifact that both the runtime and the editor consult is rare, valuable, and the thing the field has the least mature tooling for, because the generated-from-code formats dominate the JS ecosystem.

### How the field handles namespacing and precedence

This is where the formats teach the most, because almost none of them do it the way ng/Parsley currently does (fragile "first-declaration-wins"). Three distinct philosophies emerge. **Prefix-at-the-consumer** (JSP TLD, JSF) makes cross-library collision *structurally impossible* — every tag is always prefix-qualified at the page, the descriptor never owns the prefix, and the same library can appear under different prefixes on different pages. **Scope-by-import** (Angular `imports`, Blazor `@using`) makes resolution local to the consumer with no global registry, so a library's elements are only in scope where explicitly imported. **Structural precedence** (web-types) is the most sophisticated: a three-axis model of coarse `priority` enum + integer `proximity` tiebreaker + context-match scoring, plus `extension:true` for additive merge and `exclusive-contributions` to close an element to inherited attributes. By contrast, CEM, Stencil, and VS Code custom-data have *no* conflict rule at all — they assume HTML's global tag uniqueness or accrete entries with undefined last-writer behavior. The clear verdict for a greenfield format: silent first-wins/last-wins (which ng/Parsley does today, and which VS Code custom-data does) is the worst of the available options; web-types' explicit declarative precedence is best-in-class, with consumer-scoped imports a close and simpler second.

### The role spectrum and the binding model

On the binding/directionality axis the field has converged on a real best practice that ng/Parsley already partially implements and should formalize. Stencil's `name`/`attr`/`reflectToAttr`/`mutable` quartet, Angular's `transform` (booleanAttribute/numberAttribute), and Blazor's `(Value, ValueChanged)` + `:get`/`:set` all express the same hard-won idea: **the wire representation (a string attribute) is distinct from the bound value, and the push direction is separately addressable from the pull direction.** Blazor goes furthest — making two-way binding *sugar over an explicit value+event pair* and letting the consumer intercept a change *before* it applies. ng/Parsley's pull/push directionality is conceptually aligned with this, but the field's lesson is to make the value-half and the push-half **separately named descriptor fields** rather than a stringly-typed `+Changed` suffix convention (Blazor's documented weakness) — the convention is invisible and unenforceable.

### The role spectrum: required, deprecation, and docs

Two cheap, uniform mechanisms recur with near-unanimity and should be copied verbatim. First, **deprecation as `boolean | string`** on *every* node (CEM, web-types, Stencil docsTags, Vue tags) — a free deprecation channel where the string carries the migration message. The cautionary counter-example is VS Code HTML custom-data, which has *no* deprecation field and forces it into prose; its CSS sibling does better with a `status` enum. Second, **two-tier docs** — a short `summary`/`shortDescription` for listings plus a long markdown `description` for hover (CEM, JSF FeatureDescriptor, VS Code's `MarkupDescription` with explicit `kind`). On `required`, the field has learned a subtle distinction the current ng/Parsley model lacks: Blazor's `EditorRequired` and Angular's author-time-validated `required` are explicitly **tooling-time** required-ness (a warning), deliberately separated from any runtime guarantee — and Blazor's docs flag that EditorRequired's lack of runtime teeth is itself a weakness. The mature position is to offer *both* a tooling-required and a runtime-required contract and not conflate them.

### The role spectrum: identity, provenance, and composition

The formats split on whether an element has stable identity and where inherited contracts come from. CEM's `inheritedFrom` provenance plus explicit `mixins`/`superclass`, and web-types' `abstract`+`extends`+`extension:true`, let tooling **flatten inherited bindings without re-declaring them** — a capability ng/Parsley's recursive tag aliases gesture at but don't fully systematize. CEM's cleanest single idea is the **separation of declaration from registration**: a class is described once, then bound to one or more tag names via a separate export, which is exactly the decoupling Parsley's tag-alias work is circling. On identity, the tooling-only generated formats are weakest — Vue and Stencil have no stable library identity or version field, which the digests flag as the thing "a real tag-library format must add."

### The evolution stories — what the field learned the hard way

The most valuable signal is the documented *regrets*, because they are the field telling us what NOT to repeat. The throughline is **the cost of stringly-typed and convention-only design**: web-types had to deprecate a whole tranche of Vue-specific fields (`events`/`vue-argument`/`vue-modifiers`, `context`→`required-context`) because framework specifics were baked into core instead of sitting behind a `framework` discriminator. Angular reversed two architectural bets — NgModules (the global registry) abandoned for per-component `imports` with `standalone` flipping to default in v19, and `@HostBinding`/`@HostListener` reduced to "backwards compatibility only" — and now splits its ecosystem across decorator `@Input` and signal `input()`. JSP TLD's TagExtraInfo/TagLibraryValidator code-escape-hatches are the canonical reason TLDs are awkward for IDEs: the moment anything is dynamic, the logic leaves the declarative descriptor and tooling goes blind. JSF makes static tooling metadata (`expert`, `displayName`) into runtime `ValueExpression` strings, blurring the very boundary it should protect. Blazor's two-way binding needed `:get`/`:set` bolted on because the original `Value/ValueChanged`-only model was insufficient. The Svelte v4→v5 transition (its presence as a `runtime+tooling` format) is the same story in a different ecosystem: a runtime-and-tooling format reworking its component-API surface under real-world pressure. The collective lesson for a greenfield format is unambiguous: **pick the general model first, keep framework-specifics behind an explicit discriminator, prefer explicit named declarative fields over naming-suffix conventions and code escape hatches, and design the precedence model up front rather than retrofitting it.**

## Recommendations for a greenfield ng/WO format

> **[CHANGE]** marks a recommendation that departs from current WebObjects/ng practice — we have freedom to evolve both the ng component model and the WO element format.

### Greenfield ng/Parsley component-descriptor: prioritized design recommendations

These are derived from the evidence across the ten formats, judged on industry merit. Where a recommendation departs from current WebObjects/ng practice, it is flagged **[CHANGE]**.

### 1. File shape and serialization
**Recommend: a flat, attribute-oriented, non-XML serialization (JSON or a JSON-superset), NOT the verbose one-element-per-field XML of `.api`/TLD.** JSP TLD and JSF are explicitly criticized for "one-XML-element-per-property" tedium that drove the invention of convention-based escapes just to avoid authoring them. The tooling-only formats that are pleasant to read (CEM, web-types, Stencil, VS Code custom-data) are all JSON. **[CHANGE]** This replaces the XML `.api` file shape. Keep the `.papi` extension and on-disk coexistence with legacy `.api` (per the agreed plan), but make `.papi` a JSON document. Use Stencil's `docsTags`-style **open `{name, text}` annotation primitive at every level** so the format never has to gatekeep vocabulary as it evolves.

### 2. Identity and versioning
**Recommend: a stable library identity (a URI or reverse-DNS id) plus a version field at the library level — borrowed from JSP TLD/JSF's `<uri>` model.** Vue and Stencil are explicitly faulted for lacking stable identity/version, which makes multi-library resolution impossible. **[CHANGE]** ng/Parsley has no formal library identity today; add one. Critically, **separate the element's identity from its backing class/template** the way CEM separates declaration (`CustomElementDeclaration`) from registration (`CustomElementExport`): describe the element once, then bind it to one-or-more tag names. This is the principled version of what ng/Parsley's recursive tag aliases do today — keep the recursive-alias capability, but model it as named bindings to a single declaration rather than as a flat substitution table.

### 3. Multi-library precedence
**Recommend: adopt web-types' explicit declarative precedence wholesale — a coarse `priority` enum + integer `proximity` tiebreaker — combined with Angular/Blazor-style consumer-scoped imports for resolution.** **[CHANGE — highest priority change.]** This directly replaces ng/Parsley's fragile "first-declaration-wins," which the evidence shows is the worst option observed (VS Code custom-data's undefined last-writer behavior is its single biggest weakness as a library mechanism). Add web-types' `extension: true` (additive augmentation of an existing element without forking) and `exclusive-contributions` (an element declaring itself closed to inherited attributes) so Wonder/ng/app-specific layers can compose predictably. Make the in-scope element set explicit per consumer (Angular `imports` / Blazor `@using`) rather than relying on a single global registry.

### 4. The binding / attribute model (incl. two-way binding)
**Recommend: model bindings with explicit, separately-named fields for the value-half and the push-half, following Blazor's value+event pairing made into real descriptor fields.** ng/Parsley already has pull/push directionality — keep it, but **[CHANGE]** stop relying on any naming-suffix convention (Blazor's documented weakness with `+Changed`) and instead make the paired event an explicit named field. Add Angular's `transform`/coercion declaration (booleanAttribute/numberAttribute) so the **string wire type vs the bound type** is explicit — directly relevant to how WO/ng coerce attribute strings today, which is currently implicit. Keep per-binding accepted types (already present) but **[CHANGE]** upgrade them from flat strings to Vue's recursive structured type schema (enum/array/object/event, object recursing into member descriptors) so the editor can drive enum dropdowns and nested-object editors — with an explicit depth/ignore guard from day one, the lesson both Vue and CEM learned the hard way. Keep `required` and `default` (already present), but **[CHANGE]** split `required` into a tooling-time warning and a runtime contract (Blazor's EditorRequired vs a real runtime guarantee). Add VS Code's named, shared `valueSets` for DRY enumerations.

### 5. Content and slots
**Recommend: replace the coarse element-level wraps-content boolean with named, typed slots (Blazor's `RenderFragment<T>`), supporting a default unnamed slot plus named scoped slots.** **[CHANGE]** ng/Parsley's single wraps-content flag cannot express multi-region or scoped (render-prop) content; nearly every well-regarded format models slots as a first-class typed category. Also adopt JSP TLD's **body-content lexing mode** (empty | scriptless | tagdependent | opaque) so an element wrapping SQL/JS/embedded languages can declare an opaque body that directs both the runtime parser and editor highlighting. Adopt JSP TLD's **published-variable declarations with explicit scope** (NESTED/AT_BEGIN/AT_END, name-from-attribute) to document the loop/item variables WO/ng repetition and conditional elements currently expose undocumented.

### 6. Events and actions
**Recommend: model events as a first-class, separately-typed channel (Stencil/Vue/JSF), distinct from inbound props.** **[CHANGE]** ng/Parsley's flat binding list folds everything together; split outbound events and imperative/action signatures into their own typed categories. Use JSF's `method-signature` for strongly-typed action/handler bindings so the editor can validate handler shapes rather than treating actions as opaque strings.

### 7. Passthrough / attribute splatting
**Recommend: keep ng/Parsley's passthrough flag but reshape it to Blazor's `CaptureUnmatchedValues` design — a single boolean on one typed binding, with an explicit "at most one per element" rule.** This is the clean, well-bounded version; copy it almost verbatim.

### 8. Deprecation and lifecycle
**Recommend: CEM's `deprecated: boolean | string` uniformly on every node (element, binding, slot, event), the string carrying the migration message.** Add web-types' cheap lifecycle fields (`since`, `experimental`, `obsolete`). VS Code HTML custom-data's *lack* of any deprecation field — forcing it into prose — is the cautionary counter-example to avoid.

### 9. Documentation
**Recommend: keep Markdown docs (already present) and add the two-tier `summary` (short, for listings) + `description` (long, for hover) split from CEM, with an explicit markup-kind discriminator (VS Code's `MarkupDescription`).** Add VS Code's `references[]{name,url}` link field uniformly on elements, bindings, and values. Optionally adopt JSF's FeatureDescriptor visibility vocabulary (`expert` = advanced-but-visible, `hidden` = tool-internal) to tame large binding lists in the Element Reference.

### 10. Validation and the runtime-vs-tooling split
**Recommend: keep the current ng/Parsley strength of one source read by BOTH runtime and tooling — this is rare and valuable, and JSF's co-located interface/implementation block is the best precedent for preserving it.** Keep declarative cross-binding validation (already present), and **[CHANGE]** treat JSP TLD's TagExtraInfo/TagLibraryValidator code-escape-hatches as a documented anti-pattern: keep validation rules and variable computation DECLARATIVE in the `.papi` descriptor, never as a named external code class — that escape hatch is precisely why TLDs are awkward for IDEs. Finally, **[CHANGE]** make the descriptor **generatable from, and checkable against, the implementation** (Angular/Blazor's anti-drift property; Stencil's failure to validate documented slots is the named counter-example). Even while keeping `.papi` as a hand-authorable, ergonomic file (which the generated-only formats like CEM are explicitly bad at), add a validation pass that verifies the descriptor's claimed slots/bindings/events actually exist in the component — turning `.papi` into an enforced contract rather than unchecked documentation. Keep the engine-neutral, serializable on-disk form (Vue's TS-coupling and Stencil's baked-in absolute source paths are the portability mistakes to avoid).

### Summary of the principal departures from current WO/ng practice
1. Replace fragile first-declaration-wins with web-types' explicit `priority`/`proximity` precedence + consumer-scoped imports.
2. Move `.papi` from XML to JSON; flatter, attribute-oriented, with an open annotation primitive.
3. Replace the wraps-content boolean with named typed slots + body-content lexing modes.
4. Split the flat binding list into typed channels (props / events / actions / slots / styling hooks).
5. Upgrade per-binding types from flat strings to a recursive structured type schema with a depth guard.
6. Split `required` into tooling-time vs runtime; make two-way binding an explicit value+event field pair, not a suffix convention.
7. Keep validation declarative (no code escape hatch) and make the descriptor checkable against the implementation.
